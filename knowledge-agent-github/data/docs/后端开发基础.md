# 后端开发基础

## API 设计与 RESTful 规范

RESTful API 用 HTTP 方法和资源 URL 表达操作，是后端接口设计的行业标准。

### 资源与方法

| HTTP 方法 | 语义 | 示例 | 作用 |
|---|---|---|---|
| GET | 查询 | `GET /api/users/1` | 获取用户 1 |
| POST | 创建 | `POST /api/users` | 创建用户 |
| PUT | 整体更新 | `PUT /api/users/1` | 替换用户 1 |
| PATCH | 部分更新 | `PATCH /api/users/1` | 只改部分字段 |
| DELETE | 删除 | `DELETE /api/users/1` | 删除用户 1 |

### 设计要点

- URL 用名词表示资源，不用动词：`/api/users/1` 而不是 `/api/getUserById/1`。
- 复数形式：`/api/users`。
- 嵌套资源：`/api/users/1/orders` 表示用户 1 的订单。
- 查询参数用于筛选/分页/排序：`/api/orders?status=paid&page=2&size=20`。
- 版本控制：`/api/v1/users`。
- 幂等性：GET/PUT/DELETE 天然幂等，POST 不幂等（重复创建）。

### HTTP 状态码

| 范围 | 含义 | 常见 |
|---|---|---|
| 2xx | 成功 | 200 成功、201 创建成功、204 无内容 |
| 3xx | 重定向 | 301 永久、302 临时、304 缓存未变 |
| 4xx | 客户端错误 | 400 参数错、401 未认证、403 无权限、404 不存在、429 限流 |
| 5xx | 服务端错误 | 500 内部错误、502 网关错误、503 服务不可用、504 超时 |

### 一个规范接口示例

```json
// GET /api/users/1
// 200 OK
{
  "code": 0,
  "message": "success",
  "data": {
    "id": 1,
    "name": "张三",
    "email": "zhangsan@example.com"
  }
}
```

统一响应结构（`{code, message, data}`）是工程标准做法，前端解析逻辑统一。

## 接口鉴权

### 三种主流方案对比

| 方案 | 原理 | 优点 | 缺点 |
|---|---|---|---|
| Session | 服务端存会话，客户端只存 session_id | 简单、可主动下线 | 有状态，分布式要共享存储 |
| JWT | token 自包含用户信息，服务端验签不存状态 | 无状态、适合分布式 | 无法主动下线、token 泄露风险 |
| OAuth2 | 第三方授权（微信/Google 登录） | 开放平台标准 | 实现复杂 |

### Session 认证流程

```text
登录 → 服务端创建 session 并存储 → 返回 session_id（存 Cookie）
→ 后续请求带 Cookie → 服务端查 session 验证
```

- 有状态：session 存在服务端，可以随时踢人、过期管理。
- 分布式问题：多台服务器要共享 session（用 Redis 存 session）。

### JWT 认证流程

```text
登录 → 服务端签发 token（Header.Payload.Signature）→ 返回给客户端
→ 客户端请求头带 Authorization: Bearer <token>
→ 服务端验签（不需要查存储）→ 从 payload 里取用户信息
```

JWT 由三部分组成：
- **Header**：算法类型（HS256 等）。
- **Payload**：用户 ID、过期时间、自定义声明。
- **Signature**：`HMACSHA256(base64(header) + "." + base64(payload), secret)`。

**JWT 的关键认知**：
- payload 只做 Base64 编码，**不是加密**，不能放敏感信息。
- 服务端无法主动让 token 失效（只能靠过期时间，或引入黑名单/版本号）。
- secret 必须妥善保管，泄露等于所有人能伪造 token。
- 密钥要定期轮换，签名算法要校验（防 `alg=none` 攻击）。

### 密码存储

密码**绝不能存明文**，也不能只做简单哈希。正确做法：

```text
存储：bcrypt(password + 随机盐) → 存 哈希 + 盐
验证：用相同盐重算哈希比对
```

- **加盐（salt）**：每个用户随机盐，防止彩虹表攻击。
- **bcrypt / argon2**：刻意慢的哈希算法，抵抗暴力破解。
- Python 里用 `bcrypt` 或 `passlib` 库，别自己造轮子。

### 权限模型

- **RBAC（基于角色的访问控制）**：用户 → 角色 → 权限，最常用。
- **ABAC（基于属性的访问控制）**：按属性（部门、资源类型）动态判断，更灵活更复杂。
- 鉴权（Authentication，你是谁）≠ 授权（Authorization，你能干什么），两者分开实现。

## 日志与监控

### 日志分级

| 级别 | 用途 |
|---|---|
| DEBUG | 调试细节，生产通常关闭 |
| INFO | 关键业务事件（下单、登录） |
| WARN | 潜在问题，不致命（重试、降级） |
| ERROR | 错误，需要关注（异常、失败） |
| FATAL/CRITICAL | 致命错误（服务不可用） |

**经验**：生产环境一般开 INFO 以上；DEBUG 全开会有海量日志拖垮磁盘。

### 日志要素

一条合格的日志要包含：

```text
2026-08-28 10:15:30.123 INFO  [service=order] [request_id=abc123] [user=1001] 订单创建成功 order_id=8888
  ↑时间戳           ↑级别  ↑服务名      ↑请求 ID       ↑用户           ↑关键业务信息
```

- **时间戳**：排查时序问题的基础。
- **请求 ID**：把一次请求的所有日志串起来，微服务排查全靠它。
- **关键业务信息**：订单 ID、用户 ID，没有上下文信息的日志等于没记。

### 结构化日志

```python
import logging

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s %(levelname)s [%(name)s] %(message)s",
)

logger = logging.getLogger("order")
logger.info("订单创建成功", extra={"order_id": 8888})
```

结构化日志（JSON 格式）能直接被日志平台（ELK、Loki）检索分析，是现代日志标准。

### 监控指标

| 指标 | 含义 | 关注点 |
|---|---|---|
| QPS | 每秒请求数 | 流量和容量 |
| 延迟（P50/P95/P99） | 响应耗时分位数 | P99 最能暴露长尾问题 |
| 错误率 | 错误请求占比 | 超过阈值告警 |
| 数据库连接数 | 连接池占用 | 连接泄漏会打满 |
| 缓存命中率 | 缓存有效性 | 命中率低查缓存策略 |
| CPU/内存 | 机器资源 | 容量规划 |

**为什么看 P99 不看平均值**：平均值会被拖尾掩盖，P99 表示"99% 的请求都在这个延迟内"，对用户体验更有意义。

### 全链路追踪

微服务里一次请求跨多个服务，靠**trace ID + span** 串起来（如 Jaeger、SkyWalking）。每条日志带同一个 trace ID，出问题按 ID 一把捞出全链路日志。

## 常见架构组件

### 缓存（Redis）

把热点数据放内存，挡在数据库前面：

- 读多写少的场景收益最大（用户资料、商品详情）。
- 更新策略：Cache Aside（先更新库，再删缓存）。
- 经典问题：穿透、击穿、雪崩（详见 Redis 笔记）。

### 消息队列

异步解耦的利器：

```text
下单 → 写库 → 发 MQ 消息 → 通知服务异步处理（发邮件、减库存、更新报表）
```

- **削峰**：大促流量先进队列，下游按自己的速度消费。
- **解耦**：下单服务和通知服务互不阻塞。
- **异步**：用户不需要等所有下游完成。
- 常用：RabbitMQ（功能全）、Kafka（大数据量、日志）、RocketMQ（阿里系电商场景）。

### 读写分离

主库写、从库读，扩展读能力，注意主从延迟。

### 限流与熔断

- **限流**：控制单位时间请求量，超过直接拒绝或排队。算法：固定窗口、滑动窗口、漏桶、令牌桶（最常用）。
- **熔断**：下游故障时快速失败，不再调用（如 10 秒内错误率 50% 就熔断 30 秒）。
- **降级**：下游挂了用兜底方案（返回缓存数据、返回默认值）。

### 幂等性设计

重复请求不能产生重复结果：

- 下单接口：客户端生成幂等键，服务端查重。
- 支付回调：按订单号判重，处理过就返回成功。
- 消息消费：消费端记录已处理的消息 ID。

## 后端开发规范

- **参数校验**：入参在入口统一校验（用 pydantic / 参数校验库），不信任任何输入。
- **统一异常处理**：全局异常拦截，返回统一错误结构，不裸抛堆栈给前端。
- **接口幂等**：写接口考虑重复请求。
- **配置外置**：数据库密码、密钥放环境变量/配置中心，不放代码里。
- **测试**：核心逻辑写单元测试，接口写集成测试。
- **代码审查**：提交前自查 + 同事 review。

## 排查问题实战

1. **接口 500**：看服务日志（ERROR 级别）→ 找堆栈 → 定位代码行。
2. **接口慢**：看监控 P99 → 慢 SQL（EXPLAIN）→ 缓存 → 外部调用超时。
3. **偶发错误**：查"请求 ID"把一次请求的所有日志捞出来 → 找规律。
4. **数据库连接池打满**：查慢查询、连接泄漏、连接池大小配置。
5. **内存泄漏**：JVM/Python 内存监控、堆转储分析、GC 日志。
