# 知识库 Agent 项目说明

## 项目定位

这是一个部署在个人服务器上的「第二大脑」：把个人笔记、文档、代码喂进去，就能用自然语言检索问答，回答带引用出处，后续还支持联网补充和跨文档总结。

和直接问 ChatGPT 的本质区别：

- ChatGPT 靠"记忆中的常识"回答，可能编造（幻觉）。
- 本系统**只基于你喂的资料回答**，回答有据可查，能追溯来源。

一句话：**让大模型在你自己的知识库上"有依据地"回答问题。**

## RAG 是什么

本项目是一个标准的 **RAG（Retrieval-Augmented Generation，检索增强生成）** 系统：

```text
检索（Retrieve）→ 增强（Augment）→ 生成（Generate）
    找资料          拼进提示词       大模型回答
```

- **检索**：从知识库里召回和问题相关的片段。
- **增强**：把召回片段拼进 Prompt 上下文。
- **生成**：大模型基于上下文回答。

RAG 解决了大模型的三个核心问题：**幻觉**（不懂的硬编）、**知识过时**（训练数据有时间截止）、**没有私有数据**（不知道你的资料）。检索质量直接决定回答质量，是 RAG 系统拉开差距的关键环节。

## 技术栈

| 层 | 用什么 |
|---|---|
| 界面 | Streamlit（MVP 阶段，快速出效果） |
| 后端框架 | FastAPI（规划中，后续阶段） |
| 大模型 | DeepSeek（OpenAI 兼容协议），负责基于检索结果生成回答 + Agent 工具决策 |
| 向量化 | 本地 embedding 模型 BAAI/bge-small-zh-v1.5，sentence-transformers 加载 |
| 关键词检索 | 手写 BM25 + jieba 分词 |
| 语义检索 | 向量余弦相似度 |
| 混合检索 | RRF（倒数排名融合）融合 BM25 与向量 |
| 重排 | bge-reranker-base（CrossEncoder）精排候选片段 |
| 存储 | 片段文本 JSON + 向量矩阵 npy |
| 联网工具 | Tavily（可插拔，后续可换 Semantic Scholar） |
| Agent 框架 | DeepSeek Function Calling + 工具循环 |

## 核心流程

```text
文档导入 → 切片（chunk）→ 向量化（embedding）→ 存索引
→ 用户提问 → 检索 Top-K → 拼上下文 → DeepSeek 生成回答并标注来源
```

### 文档导入（ingest.py）

- 支持 md / txt / docx / pdf 四种格式。
- 先按空行分段落，段落过长再按字符切（chunk_size=400，overlap=50），尽量保留语义完整。
- 每篇切出的片段包含 `text`（内容）、`source`（来源路径）、`title`（标题）。

### 检索（retriever.py）

提供四层检索能力，层层递进：

| 方法 | 原理 | 特点 |
|---|---|---|
| BM25 | 关键词匹配（TF-IDF 改进版 + jieba 分词） | 精确匹配，对专业术语友好 |
| 向量 | embedding 余弦相似度 | 语义匹配，换说法也能找到 |
| 混合（RRF） | BM25 排名 + 向量排名融合 | 兼顾关键词和语义 |
| 混合 + rerank | 混合召回候选，CrossEncoder 精排 | 排序最准 |

### 生成（llm.py）

- 把检索到的片段拼成"参考资料"，让 DeepSeek 基于资料回答。
- 要求"只基于资料回答、不编造、标注来源"，从提示词层面约束幻觉。

### Agent 化（agent.py + tools.py）

- DeepSeek 通过 Function Calling 自主决定调什么工具：查本地知识库 `search_knowledge_base` 或联网搜索 `search_web`。
- 最多 6 轮工具调用循环，防止死循环。
- 工具做成可插拔：以后换搜索引擎只改 `search_web` 一个函数。

## 三步演进路线

1. **MVP**：跑通「文档 → 检索 → 问答」最小闭环。
2. **拉开差距**：混合检索 + rerank + 引用溯源 + 离线评测（Recall@k 对比）。
3. **Agent 化 + 部署**：联网搜索工具、跨文档总结、Docker 部署到云服务器。

## 离线评测体系

为了让"检索好不好"有数据说话，项目建立了评测体系：

### 评测集

- 60 道标注题（`eval_queries.json`），每道题标注标准答案所在的文档。
- 题型覆盖五类：关键词直白、口语化、同义改写、跨文档干扰、精确区分。
- 指标：**Recall@1**（第一下就找对的比例）、**Recall@3**（前 3 名找对的比例）、**MRR**（平均倒数排名）。

### 评测驱动优化的完整闭环

```text
纯向量检索（R@1 87.5%，40 题）
  → +BM25 混合（RRF 融合）
  → +rerank 精排（R@1 97.5%，40 题）
  → 评测集扩到 60 题（含干扰题，基线重测 R@1 96.67%）
  → 参数调优实验（候选池 10 → 5，R@1 98.33%，MRR 0.992）
  → 落地 + 交叉验证，预测与实测完全一致 ✅
```

**关键方法论**：
- 每个优化环节都有离线评测数据支撑，不靠感觉。
- 实验（tune.py）只做离线验证，结论确认后再合入正式代码。
- 评测集故意设计干扰题，防止"考的都是关键词直白的简单题"导致分数虚高。

### 评测指标的意义

- Recall@1 反映"排序准不准"：第一下就找对，用户体验最好。
- Recall@3 反映"捞得全不全"：前 3 名里能找到，说明没漏。
- MRR 综合两者，排名越靠前得分越高。

## 踩过的坑

1. **transformers 与 torch 版本不兼容**：transformers 5.x 要求 torch ≥ 2.5，本机 2.4.1 报错，需补装 torch 2.5.1。
2. **模型下载到 C 盘**：设置 `HF_HOME` 到 D 盘，避免占用 C 盘空间。
3. **Windows 环境变量不生效**：已启动的进程不会重读注册表，新配 key 要重启应用或写进项目 `.env`。
4. **conda 环境 numpy 冲突**：必须用项目 venv 的 python 跑，不能用全局 streamlit 命令。
5. **torch 同进程加载双模型 segfault**：本机内存压力下 embedder + reranker 同进程加载会崩，评测时拆两个进程分别加载，交叉验证。

## 做这个项目的收获

做这个项目最大的收获是把抽象的 RAG 理论变成了一个能跑通的系统。从最初的 MVP 到混合检索、rerank、Agent 化，每一步都踩了真实的坑：模型下载失败、torch 与 transformers 版本不兼容、embedding 和 rerank 模型同进程加载崩溃、环境变量不生效，每解决一个问题都加深了对 Python 生态、模型部署和工程流程的理解。

其次是养成了"用数据说话"的习惯。检索好不好不靠感觉，靠 60 题评测集的 Recall@1 和 MRR 说话；参数该不该调，先跑离线实验、确认收益再合入代码。调优实验预测候选池 5 能让 Recall@1 从 96.67% 提到 98.33%，落地复测完全一致，这种"实验-落地-复验"的闭环让我在做技术决策时更有底气，也是这个项目区别于一般课程作业的核心竞争力。

## 后续规划

- **评测升级**：评测粒度从"文档级"升级到"片段级/答案级"（标注答案所在的具体片段），评测集扩到 100+ 题，增加多跳问题、无答案反例。
- **端到端评测**：检索 + 生成联合评估，测回答正确率、引用准确率、幻觉率。
- **工程化**：存储升级为向量数据库（Chroma/FAISS），支持增量更新。
- **部署**：Docker 打包上云（建议至少 2 核 4G，reranker 模型需 1.5GB 内存）。
- **Agent 增强**：查询改写、多轮检索、失败重试、更丰富的工具集。
