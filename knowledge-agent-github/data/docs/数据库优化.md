# 数据库优化

数据库优化是后端工程最核心的硬技能之一。优化的方向从高到低：**SQL 与索引 → 表结构 → 架构（缓存/读写分离/分库分表）**。先查慢在哪，再对症下药，不盲目加索引。

## 慢查询优化

慢查询指执行时间超过阈值（如 1 秒）的 SQL。定位和优化的标准流程：

### 第一步：找到慢查询

```sql
-- MySQL 开启慢查询日志
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;   -- 超过 1 秒的 SQL 记录

-- 查看近期慢查询
SELECT * FROM performance_schema.events_statements_summary_by_digest
ORDER BY SUM_TIMER_WAIT DESC LIMIT 10;
```

线上也可以用 `EXPLAIN` 手动分析可疑 SQL。

### 第二步：EXPLAIN 分析执行计划

```sql
EXPLAIN SELECT * FROM orders WHERE user_id = 100 ORDER BY create_time DESC;
```

重点看：
- **type**：`ALL`（全表扫描）是最大的危险信号；`range`/`ref`/`const` 说明用上了索引。
- **key**：实际使用的索引，`NULL` 表示没走索引。
- **rows**：预估扫描行数，暴增说明优化器判断错了。
- **Extra**：`Using filesort`（排序没走索引）、`Using temporary`（用了临时表）都要警惕。

### 第三步：针对性优化

**① 补索引**

```sql
-- 有 WHERE 又有 ORDER BY，建联合索引让两者都走索引
CREATE INDEX idx_user_create ON orders(user_id, create_time);
```

**② 改写 SQL**
- 避免 `SELECT *`，只取需要的列（减少 IO 和网络传输）。
- 避免在索引列上用函数：`WHERE YEAR(create_time)=2024` 会全表扫，改成 `WHERE create_time >= '2024-01-01' AND create_time < '2025-01-01'`。
- 大偏移分页：`LIMIT 1000000, 20` 慢，改成"游标分页"：

```sql
-- 改前：要扫描 100 万行再扔掉
SELECT * FROM orders ORDER BY id LIMIT 1000000, 20;

-- 改后：只扫 20 行
SELECT * FROM orders
WHERE id > (SELECT id FROM orders ORDER BY id LIMIT 1000000, 1)
ORDER BY id LIMIT 20;
```

- 避免隐式类型转换：字符串列用数字去比会让索引失效。
- 避免 `OR` 连接非索引列；避免在 `WHERE` 中对列做运算。

**③ 减少返回数据量**：`LIMIT`、分页、只查需要的字段。

**④ 优化表结构**：字段类型选对（能用 INT 别用 VARCHAR）、大字段拆表、冗余必要的统计列。

## 索引失效场景（高频考点）

索引建了不等于一定生效。常见失效场景：

1. **对索引列使用函数或运算**：`WHERE YEAR(create_time)=2024`、`WHERE price*1.1 > 100`。
2. **LIKE 以 % 开头**：`WHERE name LIKE '%张%'` 无法用索引；`'张%'` 可以用。
3. **隐式类型转换**：字符串列 `WHERE phone = 13800000000`（数字）→ 索引失效。
4. **OR 连接非索引列**：`WHERE a = 1 OR b = 2`，a 有索引 b 没有，整个可能走全表。
5. **联合索引不满足最左前缀**：`(a, b, c)` 联合索引，`WHERE b = 1` 用不上。
6. **`NOT IN`、`!=`**：多数情况优化器放弃索引。
7. **数据量太小**：全表扫描比走索引还快，优化器直接选全表扫描。

排查方法永远是：改完 SQL 用 `EXPLAIN` 验证 `key` 列是否真的有值。

## 表结构与字段设计优化

- **选择合适的数据类型**：能用 INT 不用 VARCHAR，能用 VARCHAR(20) 不用 VARCHAR(255)。
- **避免 NULL**：NULL 让索引、统计更复杂，能 NOT NULL 就 NOT NULL（用默认值）。
- **大字段单独拆表**：把 TEXT/BLOB 类型拆到附属表，主表更紧凑，查询更快。
- **分区表**：按时间等规则分区，查询只扫相关分区，适合日志类数据。
- **范式与反范式**：适度冗余高频查询字段（如用户名），避免频繁 JOIN。

## 缓存优化

缓存是数据库优化的第一道防线，把热点数据挡在数据库前面。

### 缓存更新策略

- **Cache Aside（旁路缓存）**：读时先查缓存，没有则查库并回填；写时先更新数据库，再删缓存（或更新缓存）。最常用。
- **Read Through**：应用只和缓存交互，缓存负责回源。
- **Write Through / Write Back**：写入同步/异步穿透到数据库。

### 缓存一致性

- 先更新库再删缓存，配合"延迟双删"降低并发不一致窗口。
- 缓存设置过期时间兜底，防止长期不一致。
- 对一致性要求高的数据慎用缓存。

### 缓存问题三兄弟

见 `Redis缓存.md` 的详细分析：穿透、击穿、雪崩。这三者是缓存优化的经典面试题。

## 读写分离

单库扛不住读压力时，用一主多从：**主库写，从库读**。

```text
应用 → 写请求 → 主库
     → 读请求 → 从库1 / 从库2 ...
主库 → 复制日志 → 从库（异步复制）
```

- **主从复制**：主库把 binlog 推给从库回放，实现数据同步。
- **读扩展**：水平加从库即可扩展读能力。
- **问题**：主从延迟（读刚写的数据可能读不到），对强一致读要走主库。

## 分库分表

当单表数据量过大（几千万到亿级），即使索引再好，单机 IO/内存/磁盘也到瓶颈，这时需要分库分表。

### 分表策略

- **水平拆分（分片）**：按行分，如按 `user_id % 16` 分成 16 张表。最常用。
- **垂直拆分**：按列分，把大字段、低频字段拆到另一张表。

```sql
-- 水平分表示例：user_id % 16 决定落到哪张表
SELECT * FROM orders_5 WHERE user_id = 1000;   -- 1000 % 16 = 8 → orders_8
```

### 分库 vs 分表

- 数据量特别大且写入压力大 → 分库（分担写压力）。
- 单表数据量大但写入可接受 → 先分表。
- 一般先分表，不够再分库，最后两者结合。

### 分片键选择

- 选查询最频繁的维度（如用户 ID）。
- 尽量让大部分查询只落到一个分片。
- 分片键一旦定下很难改，要谨慎。

### 分库分表引入的新问题

1. **跨分片查询**：跨片 JOIN、聚合变复杂，需要中间件聚合或应用层处理。
2. **全局主键**：自增 ID 失效，需要全局唯一 ID 方案（雪花算法、号段模式）。
3. **分布式事务**：跨库事务变难，常用最终一致性方案（事务消息、本地消息表、TCC）。
4. **数据迁移**：扩容要重新分片，非常痛苦。

### 常见分库分表中间件

- **ShardingSphere**：功能最全，有 JDBC 和应用级接入方式。
- **MyCat**：代理模式，对应用透明但性能有损耗。
- **Vitess**：云原生时代的方案，K8s 友好。

## 架构级优化思路

```
第 1 层：SQL 优化 + 索引（成本最低，先做）
第 2 层：表结构优化
第 3 层：缓存（Redis）挡热点读
第 4 层：读写分离（主从）
第 5 层：分库分表（最后手段，复杂度最高）
```

**原则**：
- 先用 `EXPLAIN` 和数据说话，不要凭感觉加索引。
- 80% 的慢查询是 SQL 和索引问题，先解决这层。
- 分库分表是最后手段，引入的复杂度（分布式事务、跨片查询、迁移）往往超过收益。

## 常见线上事故复盘

- **索引失效导致全表扫描**：优化器统计信息过期，`ANALYZE TABLE` 刷新统计。
- **热点行锁竞争**：秒杀场景集中更新同一行，可用缓存/队列削峰、行锁改乐观锁。
- **大事务**：一个事务里做太多事，锁持有太久，拖垮并发行，尽量小事务。
- **无索引大分页**：分页越来越慢，游标分页解决。
- **连接池打满**：慢查询占满连接，先限流保护数据库，再优化慢 SQL。
